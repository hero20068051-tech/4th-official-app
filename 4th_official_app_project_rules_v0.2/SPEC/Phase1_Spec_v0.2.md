# 第4審判 交代管理Webアプリ
## Phase 1 開発仕様書 v0.2

## 1. 目的
リエントリー方式を理解していない人でも、HOME / AWAY両チームの交代を安全に管理できるWebアプリを作る。

アプリの役割は「ルールを説明すること」よりも、**利用者が通常の交代入力をするだけで、必要なルール判定と履歴管理を裏側で行うこと**。

## 2. 想定利用
- スマートフォン中心のWebアプリ。
- 第4審判が試合を見ながら使用。
- 机上・立位・両手・片手のいずれでも成立するUIを目指す。
- 初心者・中学生が大きな説明なしでも基本操作できることを目標とする。

## 3. 試合設定

### 3.1 基本
- HOMEチーム名（任意、既定値 HOME）
- AWAYチーム名（任意、既定値 AWAY）
- ハーフ時間
  - 30分
  - 35分
  - その他（カスタム）

### 3.2 飲水
`hydrationMode`：
- `NONE`
- `RUNNING_CLOCK`
- `STOP_CLOCK`

任意：
- `hydrationMemo` 例「15分頃」

`STOP_CLOCK` の場合のみ、試合中に「飲水開始」「試合再開」を操作できる。
通常の交代では時計停止しない。

## 4. 選手登録
HOME / AWAYそれぞれに独立して登録。

### 4.1 背番号
- 整数1〜99。
- 非連番可。
- 重複不可。
- 数値順に表示。
- カンマ区切り等の一括入力を許可。
- 今回の大会ルールでは試合登録最大20名。

### 4.2 選手データ
背番号を内部IDにしない。

最低限：
```text
Player {
  id
  teamId
  number
  isStarter
  isRegisteredGK
  initialAvailability
}
```

`isRegisteredGK` は「現在GKとしてプレーしているか」ではなく「GK登録選手か」を表す。
複数名をtrueにできる。

試合中に必要な派生状態はイベントログから計算する：
- currentLocation: pitch / bench
- hasAppeared
- hasExited
- reentry関連状態

### 4.3 先発人数
- 11名：通常開始。
- 7〜10名：警告し、利用者確認後に開始可能。
- 6名以下：開始不可。

### 4.4 キックオフ前変更
前半開始前は先発 / ベンチ / GK設定を自由に修正可能。
キックオフ前の先発変更は交代イベントとして記録しない。

## 5. 試合フェーズ
```text
PRE_MATCH
FIRST_HALF
HALF_TIME
SECOND_HALF
FULL_TIME
```

### 5.1 フェーズ操作
- PRE_MATCH → `前半開始`
- FIRST_HALF → `前半終了`
- HALF_TIME → `後半開始`
- SECOND_HALF → `試合終了`

`前半終了` と `試合終了` は確認ダイアログを入れる。

## 6. 時計

### 6.1 基本方針
単純な1秒ごとの加算値を唯一の正としない。
各ハーフの実開始timestampを保存し、現在時刻との差から経過を復元できるようにする。

### 6.2 保存候補
```text
ClockState {
  firstHalfStartedAt
  firstHalfEndedAt
  secondHalfStartedAt
  secondHalfEndedAt
  pausedAccumulatedMsByHalf
  activePauseStartedAt
}
```

### 6.3 飲水で時計停止する場合
- 「飲水開始」でpause開始。
- 「試合再開」でpause時間を累積。
- 表示上の経過時間からpause分を除く。

### 6.4 開始押し忘れ
前半 / 後半の実開始時刻を後から補正できる。
通常UIでは目立たせず、修正操作から利用する。

## 7. メイン画面
常に確認したい情報：
- 現在フェーズ
- 経過時間
- HOME / AWAY
- 後半なら各チームの「後半の交代 あとN回」

交代入力では登録済み背番号を大きく扱う。
通常交代 / 再出場という選択UIは作らない。

## 8. 仮入力（Draft）
HOME / AWAYそれぞれ独立したドラフトを持つ。

```text
TeamDraft {
  teamId
  pairs: [{ outPlayerId?, inPlayerId? }]
}
```

ルール：
- IN / OUT はどちらから入力してもよい。
- 確定前は自由に変更・削除可能。
- 各pairを個別に編集・削除可能。
- チーム切替後もドラフトを保持。
- ドラフトは正式な選手状態、履歴、カウントへ影響しない。
- 実施されなかった交代はドラフト破棄のみ。

## 9. 交代確定
「交代を確定」を押した時点で、その交代が実際に行われたものとしてイベントログへ追加する。

選手が交代エリアへ来た時点では確定しない。

確定時：
- 現在の実経過時間を保存。
- 入力グループ全体を合法性チェック。
- 成立すればイベント追加。
- 状態再計算。
- 短い成功表示後、次の入力へ戻る。

## 10. 交代イベントモデル
同一の試合停止中に両チームが交代できるよう、stoppageとteam groupを分ける。

例：
```text
SubstitutionStoppageEvent {
  id
  phase
  occurredAt
  elapsedMs
  teamGroups: [
    {
      teamId: HOME,
      pairs: [
        { outPlayerId: 10, inPlayerId: 15 },
        { outPlayerId: 8,  inPlayerId: 16 }
      ]
    },
    {
      teamId: AWAY,
      pairs: [
        { outPlayerId: 4, inPlayerId: 20 }
      ]
    }
  ]
}
```

後半ならHOMEは1回、AWAYも1回を独立して消費する。

同じ停止中の追加入力をどこまで同一eventとしてまとめるかは、現場で柔軟に扱えるUIにし、プロレベルの厳密な確定境界をPhase 1では作り込まない。

## 11. 通常交代 / 再出場の自動分類

### 11.1 通常交代
IN選手がその試合で未出場。

### 11.2 再出場候補
IN選手が出場済みで、現在ベンチ。

### 11.3 再出場チェック
再出場候補は次を確認：
1. HALF_TIME または SECOND_HALF か。
2. FP側の再出場解禁条件を満たしているか。
3. 再交代3名上限に抵触しないか（【PENDING】同一選手複数回ケースは独立ロジック）。
4. SECOND_HALFならそのチームに交代機会が残っているか。

### 11.4 FP側解禁条件
「ベンチにいる未出場FP交代要員」が残っていないこと。
GK登録選手はこの条件の判定から除外する。

### 11.5 HT同時成立
HTの同一交代グループ内で、最後の未出場FPが初出場し、それによって再出場条件を満たす場合、そのグループ内の再出場を許可する運用とする。

重要：pairを配列順に逐次適用して合法性が変わらないよう、**グループ全体を一括評価**する。

## 12. 9 / 3 / 3 の独立管理
次を同じカウンタにしない。

1. **使用交代要員の人数上限：9名**
2. **後半の交代機会上限：3回**
3. **HT以降の再交代選手上限：3名**

データ構造も別フィールド / 別派生値にする。

【PENDING】同一選手が複数回再出場可能な場合の3名カウント方法は、回答後に差し替える。

## 13. 入力チェック
同一team group内で：
- OUTは現在pitchのみ。
- INは現在benchのみ。
- OUTとINに同一選手を指定不可。
- 同じ選手を複数pairへ重複指定不可。
- pair間の入力順序で判定結果が変わらないこと。

エラー例：
- 「同じ選手は選べません」
- 「15番はベンチにいません」
- 「8番は今ピッチにいません」
- 「まだ10番は入れません」
- 「まだ出場していない選手がいます：17番」
- 「後半の交代は終了です」

## 14. 履歴をSource of Truthにする
初期登録状態 + 確定済みイベントログから現在状態を再構築できるようにする。

### 14.1 修正 / 取消
- 過去イベントを編集 / 削除可能。
- 変更後、先頭から時系列にリプレイする。
- 現在pitch / bench、hasAppeared、再出場可否、後半回数等を全再計算。

### 14.2 後続イベント不整合
過去修正によって後続イベントが不成立になる場合：
- 勝手に削除しない。
- 勝手に合法扱いしない。
- 影響イベントを `NEEDS_REVIEW` 等でマークする。
- 「この修正により、後の交代記録に確認が必要です」と表示する。

## 15. ローカル永続化
重要操作ごとに進行中試合をローカル保存。

対象例：
- 試合設定変更
- 前半 / 後半開始
- 交代確定
- 飲水時計停止 / 再開
- 履歴修正 / 取消
- 前半終了 / 試合終了

再読込時：
- 進行中なら「続きから再開」を表示。
- timestampベースで時計を復元。

FULL_TIMEの試合記録は、新しい試合開始操作だけで即時消去しない。

## 16. UI表示の考え方
利用者が知らなくてもよい内部情報を常時表示しない。

常時表示候補：
- フェーズ / 時計
- HOME / AWAY
- 後半の交代残数

必要時のみ表示：
- なぜ選手が入れないか
- 未出場選手番号
- 再出場内部判定
- 詳細履歴

「再出場あと2人」の常時表示は必須としない。内部では必ず管理する。

## 17. Phase 1の非ゴール
- 得点記録
- カード記録
- AT管理
- PDF / 画像出力
- クラウド同期
- 複数端末共有
- 写真読取
- 選手名必須化
- 詳細レポート
- AI会話
- 脳震盪交代の専用UI
- 退場選手等の詳細な出場不可状態

## 18. 実戦テスト方針
完成後、実戦 / 模擬試合と中学生ユーザーで確認する。

観察する：
- 説明なしでどこまで操作できるか
- 迷った場所
- 操作が遅れた場所
- 押し間違えた場所
- 不要だった表示
- 欲しかった情報
- 想定外の交代ケース
- 分からなかった言葉

テスト時は先に操作方法を教えすぎない。
「どこ押すの？」となった箇所自体をUI改善材料とする。

作業前に `PROJECT_RULES/00_READ_FIRST.md` から順に必ず確認する。

## 20. Phase 1 完成版での実装確定事項（v0.2からの追記）

実装・実機テスト（Mac / Pixel 9a）を通じて、v0.2本文には詳細を書いていなかった箇所の具体的な実装方法が確定した。判定ロジック（9名 / 後半3回 / 再交代3名、通常交代・再出場の自動判定）自体は無変更。【PENDING】（本文20.9参照）にも新しい解釈を加えていない。

### 20.1 同一停止のHOME/AWAY関連付け（10章の補足）
「現場で柔軟に扱えるUI」の具体化として：
- 反対チームの交代確定が、試合内経過時間で約60秒以内なら自動的に同じ停止として関連付ける（あくまで便宜上の初期値で、ルールではない）。
- 履歴画面から「同じ停止としてまとめる」「まとめを解除」を手動でいつでも行える。
- 関連付けは表示用の情報のみで、9/3/3のカウントや合法性判定には一切使用しない。
- 履歴表示では、関連付いたHOME/AWAYの交代を1つの枠にまとめ、色（HOME=青／AWAY=橙）とチーム名ラベルの両方で区別する（色のみに依存しない）。

### 20.2 飲水リマインド表示（3.2章の補足）
`hydrationMemo` に含まれる最初の数字を目安分数として読み取り、以下を試合画面へ表示する（あくまで目安表示であり、実施可否はMCM・審判の判断が優先）。
- 目安の約1分前〜目安時刻未満：「まもなく飲水の目安です」
- 目安時刻以降：「飲水の目安時刻です」
- それ以外：「💧 飲水あり｜（メモ内容）」
- メモに数字が無い場合は上記の時刻判定を行わず、メモをそのまま表示する。

飲水の完了状態（`hydrationCompletedByHalf`）を前半・後半で別々に保持する。
- `RUNNING_CLOCK`：「飲水を実施」ボタンで完了扱いにできる。時計は止めない。目安の1分以上前に押した場合は「まだ飲水目安時刻より前です。飲水を実施しましたか？」の確認を挟み、確定操作をしてから完了扱いにする。目安1分前以降は確認なしの1タップで完了扱い。
- `STOP_CLOCK`：既存の「飲水開始」→「試合再開」が完了した時点で自動的に完了扱いにする。飲水開始/試合再開自体の時計停止・再開の挙動は無変更。
- 完了扱いになったハーフでは、そのハーフ中はリマインドを再表示せず「💧 飲水済み」とだけ表示する。

### 20.3 開始時刻の補正UI（6.4章の補足）
「時刻」ではなく「経過時間（分・秒）」を直接入力する方式に確定した。
- 入力は分・秒を別々の数値欄に分ける（コロン入力が困難な端末があるため）。
- 0〜180分の範囲外は補正を反映せず、エラーを表示する（明らかに異常な値の無警告反映を防止）。
- 復帰時の経過時間が180分を超えている場合は、状態から導かれる注意表示を出し、補正欄を自動的に開いた状態で表示する（時計の仕組み自体は変更しない。あくまで気づきやすくする表示上の対応）。

### 20.4 メイン画面の常時表示（7章の補足）
「現在フェーズ」の表示に、前半・後半中のみハーフ時間を付記する（例：「前半｜25分ハーフ」）。設定したハーフ時間を超えても自動での前半終了・試合終了は行わず、「規定時間◯分を経過」という表示のみ行う（アディショナルタイムがあるため）。

### 20.5 一時的な操作エラーと状態由来の説明の分離（9・13章の補足）
交代入力画面のメッセージを2種類に分けて管理する。
- 状態から導かれる説明（例：後半交代0回時の「後半の交代を3回使っています」、リエントリー状況の「あと1回｜リエントリー2/3名」等）は保存せず、毎回その場の状態から計算して表示する。
- 一時的な操作エラー（選べない選手をタップした理由、確定失敗時のエラー等）は、チーム切替・入力取りやめ・交代確定・履歴取消・履歴編集・フェーズ変更のいずれかで確実にクリアする。

後半の交代機会が0回になったチームは、OUT/IN・「＋もう1組」・「交代を確定」を実際に操作不可にし、理由を表示する（もう一方のチームには影響しない）。

### 20.6 背番号一括入力の解釈幅（4.1章の補足）
半角カンマ・読点「、」・全角カンマ「，」・空白に加え、全角数字（IMEの全角入力）もNFKC正規化により受理する。1〜99範囲チェック・重複チェックは変更していない。

### 20.7 ハーフ時間の自由入力（3.1章の補足）
30分・35分以外の自由入力値も、選択中であることが視覚的に分かるようにする（枠の強調＋チェック表示）。

### 20.8 モバイル表示の安定化
スマートフォン実機（Pixel 9a）で確認された、横方向のわずかなズレ・ピンチズーム後の表示ズレに対し、レイアウト・overflow設定を調整した。ピンチズーム自体は禁止しない。

### 20.9 未確定のまま維持されている事項
以下は本追記時点でも【PENDING】であり、独自解釈を加えていない。
- 同一選手が複数回リエントリーできるか。
- HTで「最後の未出場FPを出す」と「別選手をリエントリー」を同一グループ内で同時に成立させる解釈（11.5章は中村氏確認済みの運用として実装済みだが、複数回リエントリーの扱いとは別問題として区別する）。
